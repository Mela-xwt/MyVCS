# MyVCS 五项 P1 新增功能设计与开发说明书

> **项目**：基于 Rust 的文件版本控制系统 MyVCS 的功能扩展与性能优化  
> **基础版本**：`3.zip`  
> **目标平台**：openEuler 22.03 LTS  
> **参考版本**：`1.zip`、`2.zip`、`4.zip`、`5.zip`、`6.zip`  
> **文档状态**：设计方案，新增功能尚待移植与验收

## 1. 项目背景和整体目标

小组决定使用 `3.zip` 作为基础工程。该版本已扩展 SSH 远程协作、增量传输、权限控制、引用事务、操作记录及历史恢复等能力。此次开发不重复移植这些已有能力，而是围绕文件管理、工作区恢复、存储优化与环境诊断，增加五项 P1 功能。具体实现以基础版本真实源码接口为准，不应机械复制其他版本代码。

| 编号 | 新增功能 | 参考源码包 | 目标 |
| --- | --- | --- | --- |
| F01 | 智能文件忽略 `.myvcsignore` + `check-ignore` | `1.zip`、`4.zip`、`5.zip` | 统一过滤不需跟踪的文件，并解释忽略原因 |
| F02 | 单文件恢复 `restore` + 暂存差异 `diff --staged` | `1.zip`、`2.zip`、`4.zip` | 精确恢复文件、明确下一次提交的修改 |
| F03 | `stash` 临时工作区快照 | `5.zip` | 安全保存、恢复未提交工作现场 |
| F04 | Delta 增量存储链深度优化 | `6.zip` | 降低深链对象的读取和校验成本 |
| F05 | `doctor --json` 系统诊断 + `stats` 仓库统计 | `2.zip`、`4.zip` | 提高环境与仓库状态可观测性 |

### 开发原则

- 保留现有 13 条基础命令及 `3.zip` 的远程同步和事务能力。
- 在独立分支开发，每项新功能都配备自动化测试与使用文档。
- 修改工作区、索引或对象引用前必须执行覆盖检查和一致性保护。
- 区分**功能已实现**、**测试已通过**与**性能收益已证实**。
- 所有测量结论必须绑定源码提交、硬件及系统环境、输入数据和脚本。

## 2. F01：智能文件忽略

### 2.1 目标与参考

新增根目录 `.myvcsignore` 和 `check-ignore` 命令，防止未跟踪的日志、缓存及编译目录被批量加入仓库。参考 `1.zip`、`4.zip` 的忽略规则实现，及 `5.zip` 的规则查询接口。

### 2.2 用户操作示例

在仓库根目录新建 `.myvcsignore`：

```gitignore
# 构建目录
 target/
*.log
cache/
!important.log
```

> 实际使用时请去掉 `target/` 前多余的空格。具体否定规则与目录规则以最终实现的匹配语义为准。

```bash
myvcs status
myvcs add .
myvcs check-ignore target/debug/app
```

`check-ignore` 可返回是否忽略、规则内容和规则来源；输出格式在 CLI 定稿时统一。

### 2.3 实现思路

1. 加载仓库根目录规则，解析注释、空行、通配符、目录规则和否定规则。
2. 将规则匹配封装成独立接口，供工作区扫描调用。
3. `status`、目录递归 `add`、未来的 `stash --include-untracked` 复用统一过滤结果。
4. 已跟踪文件不因新规则而自动取消跟踪。
5. `.myvcs` 等内部元数据及不安全路径不能被否定规则重新纳入。

**推荐模块**：在 `src/repo/` 下建立 `ignore.rs`，与现有 `workspace.rs` 进行接口集成；具体目录结构以 `3.zip` 为准。

### 2.4 测试与验收

| 场景 | 预期结果 |
| --- | --- |
| 忽略 `.log` | 未跟踪日志不出现在 `status` 或目录批量暂存中 |
| 目录规则 `target/` | 子文件被过滤 |
| 否定规则 | 符合约定的重新纳入逻辑 |
| 已跟踪文件匹配忽略规则 | 仍能检测修改 |
| `check-ignore` | 命中规则与行号/来源准确 |
| 路径越界、内部目录 | 不发生误跟踪和越权访问 |

**完成标准**：规则一致、边界安全、原有命令回归通过；如果声称提升扫描性能，还需提供相同数据集下的对照耗时。

## 3. F02：单文件恢复与暂存区差异分析

### 3.1 目标与参考

- `restore`：从 HEAD 或指定提交恢复单个文件，不执行整库回退。
- `restore --staged`：撤销指定文件的暂存变更。
- `diff --staged`：比较 HEAD 快照与索引所表示的下一次提交状态。

参考 `1.zip`、`4.zip` 的文件恢复设计，和 `2.zip` 的暂存区差异命令。

### 3.2 操作示例（拟新增接口）

```bash
myvcs restore README.md
myvcs restore --source <commit-id> README.md
myvcs restore --staged README.md
myvcs diff --staged
myvcs diff --staged README.md
```

| 操作 | 工作区 | 暂存区 | HEAD |
| --- | --- | --- | --- |
| `restore README.md` | 恢复指定文件 | 不变 | 不变 |
| `restore --staged README.md` | 不变 | 恢复 HEAD 中的指定文件状态 | 不变 |
| `diff --staged` | 不变 | 只读 | 不变 |
| `reset --hard <commit>`（已有功能） | 整库重置 | 整库重置 | 移动 |

### 3.3 实现思路

`restore`：解析来源提交 → 读取其文件路径/OID 映射 → 读取并验证 Blob → 检查目标路径及覆盖风险 → 使用基础版本安全写入与锁/事务接口更新指定文件。

`diff --staged`：获取 HEAD 文件映射 → 结合索引的新增、修改及删除条目构造待提交快照 → 对比两组内容 → 输出统一差异格式。**不能直接比较工作区与 HEAD**，否则会把未暂存修改误认为已暂存。

推荐以 `src/repo/restore.rs` 封装恢复逻辑，并复用现有 diff、对象读取及安全路径接口。

### 3.4 测试与验收

- 恢复单个文件后，其他文件、HEAD、未指定的索引条目不变。
- 可从旧提交恢复文件，恢复字节与目标版本一致。
- `diff --staged` 只显示已暂存新增/修改/删除，未暂存变化不得混入。
- 拒绝路径越界、危险符号链接覆盖及未明确允许的数据丢失。
- 异常失败不留下损坏索引或部分文件状态。

## 4. F03：Stash 临时工作区快照

### 4.1 目标与参考

`3.zip` 尚无完整的 `stash` 命令；参考 `5.zip` 的 `stash push/list/show/apply/pop/drop`、事务与安全机制，增加未提交现场的保存与恢复。不能直接照搬，因为 `5.zip` 的说明明确指出其 GC 未完整保护 stash 对象。

### 4.2 拟新增命令

```bash
myvcs stash push -m "暂存开发中的修改"
myvcs stash push --include-untracked
myvcs stash list
myvcs stash show 0
myvcs stash apply 0
myvcs stash pop 0
myvcs stash drop 0
```

- **push**：保存工作区和索引状态，成功持久化后才清理相关现场。
- **list/show**：显示快照及其受影响文件。
- **apply**：恢复快照但保留记录。
- **pop**：只有恢复成功，才移除记录。
- **drop**：移除快照引用，对象回收交由安全 GC。

### 4.3 数据与实现方案

Stash 记录建议包括：基础提交 OID、时间、消息、工作区文件映射、暂存区新增/修改/删除状态、是否包含未跟踪文件。具体数据模型需要与 `3.zip` 的对象格式、引用事务和索引结构兼容。

**保存流程**：持有写锁 → 检查当前未完成操作 → 收集待保存文件 → 将数据存为内容寻址对象 → 原子发布 stash 引用和元数据 → 持久化成功后恢复相应工作区状态。

**恢复流程**：检查 stash 对象完整性 → 检查目标工作区覆盖风险 → 按约定进行三方状态恢复/冲突报告 → 更新工作区和索引 → 成功后按 `apply/pop` 语义保留或删除引用。

### 4.4 关键安全问题：GC 根集合

如果 stash 快照保存的 Blob 不被任何正常提交引用，而 GC 只遍历分支和 HEAD，那么执行 GC 后可能失去恢复数据。因此必须把**有效 stash 引用**加入可达性根集合，并为对象校验和生命周期设计测试。

同时确认原有远程引用、接收隔离区、事务记录、reflog 恢复引用不会因为此项开发受到破坏。

### 4.5 测试与验收

| 流程 | 要求 |
| --- | --- |
| `push → list → apply` | 内容与暂存状态准确恢复、快照保留 |
| `push → pop` | 仅成功恢复后删除快照 |
| `push → gc → apply` | 仍可恢复所有快照数据 |
| 多个 stash | 记录独立、索引稳定 |
| 当前工作区有冲突 | 不静默覆盖、保留恢复机会 |
| 恢复过程中断 | 可识别并处理未完成状态 |
| `drop → gc` | 已无引用对象可按规则回收 |

**完成标准**：GC 前后可正确恢复，工作区/索引一致，故障时不会丢失快照，原有远程协作测试通过。

## 5. F04：Delta 增量存储链深度优化

### 5.1 目标与参考

参考 `6.zip` 的新建 Delta 链深度上限策略。`3.zip` 本身已有 Delta 深度相关防护，因此这里应开展**已有策略改进和效果验证**，而不是重复加一层无意义的限制。

### 5.2 设计要点

将下列阈值区分管理：

1. **旧对象读取深度上限**：保留对已存在合法历史链的兼容。
2. **GC 新增 Delta 链深度上限**：候选方案限制为 **8 层**。

GC 选择 Delta 候选时先计算基对象链深度，若生成目标链将超过 8 层，则尝试其他候选或保留完整对象。任何新 Delta 都要通过逻辑对象 SHA-256 校验；不得为了缩短链而改变提交所代表的文件字节。

### 5.3 实现流程

```text
GC 选择目标对象
  → 查找候选基对象
  → 检查候选基础链深度
  → 是否满足新链深度限制？
      ├─ 否：换候选或保留原始/完整对象
      └─ 是：计算 Delta 与压缩收益
                → 达到收益门槛则安全写入
                → 校验重建内容和 OID
```

建议修改已有 `gc_verify.rs` 和 Delta 辅助函数，新增独立的写入阈值常量与测试，避免将读路径兼容阈值直接从 64 降为 8。

### 5.4 对照实验

在相同 openEuler 环境与固定随机种子下，比较优化前基础版本和优化后版本。

| 数据组 | 测量项目 |
| --- | --- |
| 多次局部编辑的文本 | GC 耗时、verify 耗时、最大链深度、存储占用 |
| 局部修改的大二进制文件 | 对象重建耗时、峰值内存、存储占用 |
| 随机不可压缩数据 | 完整对象回退与额外开销 |

可增加链深度为 4/8/16/32 的参数组，研究空间与时间权衡。注意：更短的链**可能增加磁盘占用**，不要预先宣称所有场景均加速。

### 5.5 验收标准

- 新生成 Delta 的实际链深度不超过指定阈值。
- 历史合法对象仍可读。
- GC 前后 `verify` 通过，所有历史恢复文件哈希相同。
- 深链、缺失基对象、损坏链、重复 GC 等异常场景受覆盖。
- 性能结论附原始日志、脚本、环境和版本哈希。

## 6. F05：系统诊断与仓库统计

### 6.1 目标与参考

结合 `2.zip` 的 `doctor --json` 和 `4.zip` 的 `stats`，增加统一的环境能力与仓库资源状态展示。`3.zip` 已具备部分 openEuler/Linux I/O 检测路径，应优先复用。

### 6.2 新增命令

```bash
myvcs doctor
myvcs doctor --json
myvcs stats
```

**Doctor 建议字段**：OS、内核、架构、仓库文件系统、NUMA、PSI、ETMem、`mmap`、`posix_fadvise`、`madvise`、实际采用的 I/O 缓冲区策略。

**Stats 建议字段**：提交、本地分支、远程跟踪分支、标签、所有对象、可达对象、对象存储字节数、暂存区条目数。

### 6.3 输出设计示例（非实测结果）

```json
{
  "system": {
    "os": "openEuler 22.03 LTS",
    "kernel": "detected-kernel",
    "architecture": "x86_64"
  },
  "filesystem": { "type": "ext4" },
  "capabilities": {
    "numa": false,
    "etmem": false,
    "psi": true
  }
}
```

无法可靠探测时应使用 `unknown`/`null` 和说明，不可把默认值假装为检测结论。

### 6.4 实现思路

`doctor`：读取 OS 及内核信息 → 检查仓库所在挂载点和运行时能力 → 读取 MyVCS 优化配置 → 形成结构化诊断对象 → 输出文本或 JSON。

`stats`：读取仓库引用、索引和对象目录 → 根据明确口径统计 → 输出结果；需要区分总对象、可达对象、本地分支、远程跟踪分支等概念。

可考虑将功能分别放到 `src/repo/doctor.rs` 与 `src/repo/stats.rs`，前提是与基础工程的现有模块划分兼容。

### 6.5 验收标准

- `doctor --json` 可被解析，字段与真实环境相符。
- ETMem/NUMA/PSI 不可用时不崩溃。
- `stats` 在空仓库、多分支、远程引用和 GC 前后结果正确。
- 统计和诊断命令不应改变仓库状态。
- **检测到优化功能可用，不等于证明优化有效**；性能收益必须单独测试。
