# 阶段 3 运维与故障恢复

运行记录和支持范围见同目录 [README.md](README.md)。

## 仓库升级

1. 停止所有访问该仓库的服务和客户端进程，包括 GC、旧版程序和已建立的 SSH 会话。
2. 备份完整仓库目录，保留对象与元数据。
3. 使用新版 `myvcs --repo PATH upgrade --quiescent`，再运行 `verify`。
4. 服务端切换为新版二进制后恢复访问。旧客户端通过新版服务访问；旧二进制不得直接操作升级后的目录。

不提供原地降级命令。不得手工改小格式版本或将旧松散引用复制回来冒充当前状态。升级中断后重试相同命令；已经提交版本 2 标记而状态文件丢失或损坏时明确失败，应从完整备份恢复，不回退到可能过期的松散引用。

## 引用更新结果不确定

引用发布成功后，网络可能在成功响应到达之前断开。此时先重新 fetch 或查看远端引用；核对目标 OID 是否已生效，再决定是否重试。不要仅根据客户端退出码假设事务没有提交。

引用事务的原子范围是所有指定引用、HEAD 对应记录和成功更新 reflog。工作区、索引、多文件恢复，以及外部策略配置不在这一个原子范围内。进程中断测试也不等同于断电和存储设备故障测试。

## 误 reset、误删分支与强制更新

```bash
myvcs reflog
myvcs recover FULL_COMMIT_OID rescue/topic
myvcs checkout rescue/topic
myvcs verify
```

`recover` 创建新分支，并要求目标仍在保留的 reflog 中。不要先过期日志再尝试恢复。GC 保留日志端点的全部历史；显式日志过期后，只受那些日志保护的历史可被回收。升级不会补建升级前的 reflog。

`--force-with-lease` 必须提供完整、明确的期望旧 OID，并要求服务端独立授予 force 权限。它只防止覆盖与指定期望不符的引用，不自动判断被丢弃的工作是否有价值。改写前可创建备份分支；备份分支也需要相应写权限。

## 合并中断与冲突

正常冲突逐项编辑并 `add`/`rm`，然后 `commit`；提交会保留双方父提交。取消本次合并使用 `merge --abort`。如果工作区写入或 abort 中途被终止，再运行 abort。不要删除合并恢复状态来绕过“尚未完成”的保护检查。

多个最佳共同祖先、文件/目录碰撞以及大小写歧义属于本轮明确拒绝的情形。二进制和超过文本计算预算的内容转为文件级冲突。不存在自动重命名检测或递归虚拟合并基础。

## 权限与审计保留

仓库的策略文件由服务器管理员管理，不能通过提交树下发。可信 SSH 身份与提交作者相互独立；修改 `user.name` 不会获得另一人的访问权限。分支规则限制写入，仓库 read 权限仍允许读取该仓库全部历史。

受限团队密钥必须使用固定 forced command，且不具备同一账户的任意 shell 或文件写入通道。拥有操作系统账户或管理员权限的人仍能直接改写策略、仓库与审计文件；本实现不提供针对这类权限的防篡改审计。

成功更新记录与引用状态一起提交，长期审计必须在显式 reflog 过期之前导出。拒绝、读取等尝试记录使用单独的有界存储；容量不足时服务拒绝相应操作，需要管理员按保留策略导出并清理。不得依赖无限累积或静默丢弃审计记录。

## 中断残留与备份

对象接收失败可能留下不再可达的完整对象；只有经过闭包校验并成功发布的引用才生效。正常错误会清理临时事务目录，强杀残留沿用阶段 1/2 的离线维护流程：停止所有使用仓库的进程后再处理临时目录，不要在线删除仍可能被传输使用的隔离基础或输出快照。

备份应包含格式标记、当前引用状态、对象、配置、策略及需要保留的审计记录。备份和恢复期间停止写入，以得到一致的副本。恢复完成先 `verify`，再恢复团队访问。
